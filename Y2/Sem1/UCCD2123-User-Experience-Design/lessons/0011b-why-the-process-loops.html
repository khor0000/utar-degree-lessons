Why the process loops

The process is iterative because evaluation follows every activity and can send the team back to any of them, so each round refines the design. The process has no fixed start and no fixed order.

Lesson 11 showed the loop. This lesson explains why it has to be a loop, and what the slides mean by "process" and "stage".

Why this matters. Tutorial 2 Q1 asks what the process is and why it is iterative. Every later lesson assumes you can return to an earlier activity.

Looks like a recipe: step 1, step 2, step 3, and then it is done. It differs because the steps are not fixed. A recipe is the picture the book rejects. Here the steps are the four activities, and you may enter at any of them and return to any of them.

"Process" and "stage" in the slides

The slide calls the UX process a "Generic UX Process Model": "practical steps a team follows to take a product from an idea to a launched, usable experience" (Lecture 2, PDF p4). That is the whole sequence of activities across a project.

A stage is the slide's word for one of the four activities. The same slide says "the process can start at any stage", next to the four parts it names (Lecture 2, PDF p4). The book says "point" for the same idea: "the process can start at any point" (Benyon ch3, 3.2, PDF p78). A stage is a place you can enter, not a numbered step.

"Done once from top to bottom" is the linear picture. The slide sets "Linear Process" against "Iterative Process" (Lecture 2, PDF p2), and the book takes the iterative side: "It is an iterative process, not a linear one" (Benyon ch3, 3.1, PDF p77). So that phrase describes the view the book rejects, not its own view.

Evaluation follows each activity, but no next step is fixed

The book's rule is that "any of the other design activities will be followed by an evaluation" (Benyon ch3, 3.2, PDF p83). That attaches an evaluation to each activity. It does not say what comes after it. You might reasonably read it as a fixed chain: understanding, evaluation, design, evaluation, envisionment, evaluation. The book's own example is one path among many: "understanding might be evaluated and a prototype built and evaluated and some aspect of a physical design might then be identified" (Benyon ch3, 3.2, PDF p78). The word "might" marks an example. Figure 3.2 agrees: its three double-headed arrows each join evaluation to one other activity, and none joins understanding to design, so it fixes no order.

Why any activity can send the team back

Evaluation finds problems, and each problem points to the activity that caused it. The team goes back there, repairs the design, and evaluates again. The book's reason is that "both the understanding of needs and desires and design solutions evolve during UX design" (Benyon ch3, 3.1, PDF p77). Iterative means this return is repeated. Each round refines the design; the team does not start again from scratch.

Round 1, design. The first pick-up screen asks for the tracking number before anything else.

Round 1, evaluation. Three of four students cannot find their tracking number. That is a problem with the design.

Back to design. The problem sends the team back to the activity that caused it.

Round 2, design. The screen asks for the phone number first, then lists the parcels.

Round 2, evaluation. All four students find their parcel in under 20 seconds. One asks whether a text can say when it is ready.

Back to understanding. That new need starts the next round.

The lecture gives the same reason in other words: UX design is "a cyclic method for creating user-centred products by continuously learning about users and refining the design" (Lecture 2, PDF p3). It also says the requirement itself is checked through a prototype, so "the process is often iterative" (Lecture 6, PDF p3).

Where ideation sits

Lesson 11 flagged a conflict over ideation. The book uses it for generating ideas: "design involves the creative process of idea generation, 'ideation'" (Benyon ch3, 3.2, PDF p79). It is not a fifth activity. The book also uses it for the "creative leap" that turns stories into requirements (Benyon ch7, PDF p176), and for sketching ideas during envisionment (Benyon ch8, PDF p213). So ideation sits mainly in design, and it runs into the work on either side.

The slide swaps the two meanings, so this lesson follows the textbook. Lecture 6 (PDF p3) uses "ideation" a third way, for evaluation, which is another reason to use the book's word.

Produce it • closed book

Close this lesson. In a few sentences, explain why the UX design process is iterative, and why "done once from top to bottom" is not the book's view. Use one example that starts from evaluation. Then answer T2 Q1 in your own words.

reveal model answer

The process is iterative: the team goes round the four activities in repeated rounds, and each round refines the design. It can start at any activity, the activities can happen in any order, and evaluation follows each one. For example, a team starts from an app with poor reviews (evaluation). It finds that the menu layout is the problem, so it returns to design, builds a prototype (envisionment) and evaluates again. "Done once from top to bottom" describes the linear picture, which the book rejects: it has no fixed start or order, and any problem found sends the team back to the activity that caused it.
