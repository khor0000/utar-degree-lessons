Evaluation families in use

Summative evaluation is done on a finished product, and formative evaluation is done while the design can still change. The three families differ in who does the checking and when, and the book recommends combining an expert family with a participant family.

Why this matters. Before you choose a method for a draft, you need to know whether you are shaping the design or judging it, and whether real users can test it yet.

Focus on. The two stage words, the family table, and the order the families are used in.

Formative and summative differ by when the result is used

The book says a test of early prototypes is "sometimes termed formative evaluation because the results help to form – or shape – the design" (Benyon ch10, 10.1, PDF p271).

Formative evaluation: evaluation done while the design is still changing, so its results shape the next version. Benyon ch10, 10.1, PDF p271

Summative evaluation: evaluation done when a product is complete, to show it meets performance criteria or a standard such as ISO 9241. Benyon ch10, 10.1, PDF p271

FormativeSummative
The one-second ruleThe result changes the design while it is still changing.The result judges a finished product against criteria.
Why both matterProblems found early are the ones the designer can still fix.It gives evidence that the product meets a customer's standard, such as required task times.
When to use whichMock-ups and prototypes.The complete product, against ISO 9241 or in-house guidelines.

Summative evaluation is done on the finished product. The stage decides the label, not the method. The book says heuristic evaluation "should not be used as a summative assessment" (Benyon ch10, 10.3, PDF p277).

Where the slides differ. Lecture 9 ties within-subject designs to formative evaluation and between-subject designs to summative (PDF p19). The book does not make that link. It labels by stage, so this lesson follows the book.

The umbrella term is missing

The book gives no single term that covers both. It names them side by side (PDF p271), and the lecture's "Stages of Evaluation" slide lists four stages, not the pair (Lecture 9, PDF p4). Working label, not in the book: evaluation timing. Use it as a memory aid only.

Three families, one table

The book defines the families in one passage (Benyon ch10, 10.1, PDF p268). Expert-based methods are used by "a usability expert, or a UX designer". Participant-based methods recruit people. Data analytics gathers data "once the system or service is deployed".

FamilyTypical methodsWho takes partWhen it fits
Expert-basedHeuristic evaluation; cognitive walkthrough; informal expert reviewOne or more UX experts, who may adopt a personaEarly, from mock-ups: "particularly early" (PDF p275)
Participant-basedUser testing; cooperative evaluation; participatory heuristic evaluation; controlled experimentsReal people. The book says "at least three and preferably five" per test (PDF p286)Once there is a prototype. Must be used "at some point" (PDF p268)
Data analyticsPage views; bounce rate; heat maps; A/B testingReal users of the live system, whose use is loggedAfter implementation (PDF p269)

Two terms in that table need a gloss. Bounce rate is the share of visitors who leave at once, without looking at any content (Benyon ch10, 10.2, PDF p273). Participatory heuristic evaluation is a heuristic review where participants join the experts as work-domain experts (PDF p280).

Data analytics is a family, not a field

Data analytics is one evaluation family. HCI is a field of study, defined in Lecture 1 as "the study of how people interact with technology" (PDF p16).

Data analyticsHCI
The one-second ruleA method that tests a live system with logged data from real use.A field that studies how people interact with technology.
Why both matterIt shows what many real users do.The fields share goals and overlap in usability and user research (Lecture 1, PDF p15).
When to use whichA question about a live page, such as which of two versions gets more clicks.A question about the field, not one design.

Must a project use all three, and in what order?

The book does not say every project must use all three. It says participant methods "must be used at some point" (PDF p268). For a simple project it says to combine expert-based and participant methods, and to run the expert review first, so its results "help to focus" the participant testing (Benyon ch10, 10.5, PDF p284). Analytics needs a running system, so it comes last.

Sketch or mock-up. An expert reviews the idea before users see it. Experts "will often pick up significant usability or UX issues quickly" (PDF p268).

Working prototype. Real people try it, because experts "sometimes miss detailed issues that real users find difficult" (PDF p268).

Complete product. A summative check against criteria, or a statistical evaluation of the near-complete product "in its intended setting" (PDF p268).

Live system. Data analytics runs on real use. A/B testing randomly assigns users to two versions (PDF p275).

Working rule (not in the book). Use expert review on a sketch, participant tests on a prototype, and analytics once live. Expert review is a first step, but it "will not find all problems" (PDF p278), so it does not replace participant tests.

A campus food-ordering app has a mock-up, and the team later launches it. Name one expert-based method and one data analytics method, and say when each fits.

reveal model answer

Expert-based: heuristic evaluation. One UX expert checks the mock-up against heuristics such as visibility and feedback. It fits early, before users see it.

Data analytics: A/B testing. Two menu layouts are randomly split between live users, and the team compares click-through rates. It fits after launch.
