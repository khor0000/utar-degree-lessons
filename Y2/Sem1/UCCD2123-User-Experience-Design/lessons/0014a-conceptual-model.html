Conceptual model: objects and relationships, no screens

A conceptual model is the designer's abstract description of the main objects in a system, their attributes and how they relate. It names no screen, button or device. It is not the picture a user forms in their head, which is a mental model.

The mental model from Lesson 14 is the user's picture. This lesson covers the designer's side, and the next box says where the two differ.

Why this matters. Tutorial 2 Q4 asks you to separate the designer's plan from the user's understanding. Mixing these two up is the usual mistake.

Focus on. The three parts of a conceptual model, and the test for whether a model is abstract.

Skip for now. Object-action analysis, which is the book's method for building a conceptual model, and entity-relationship notation beyond the 1 and m labels.

How you'll be tested. Tutorial 2 Q4 in writing, closed book.

Looks like the mental model (Lesson 14), but whose picture it is differs. Both name the same things. The conceptual model is the designer's written plan; the mental model is a user's belief, built by using the app. Chapter 2 uses "conceptual 'models'" loosely for people's understanding (Benyon ch2, PDF p60). Chapters 3 and 9 mean the designer's description, which this lesson uses.

What it is

Conceptual model: a description of the main objects in a system, their attributes, and the relationships between them. Benyon ch3, 3.6, PDF p97

It is a diagram or list that the designer writes, not software that runs. It holds three kinds of content, each defined here:

  • An object is a thing the system deals with, such as an order.
  • An attribute is a fact that describes one object, such as the pickup time of an order.
  • A relationship links two objects. The book writes it as how many of one can link to how many of the other, using "1" for one and "m" for many (Benyon ch9, 9.4, PDF p253).

The book gives two reasons for drawing one. The model is the basis for how the content is organised, and for any metaphor the design uses. And a clear model helps people form a good, accurate mental model of the system (Benyon ch3, 3.6, PDF p97).

What one looks like

Take the canteen meal from Lesson 14, and draw only the objects and how they relate. Step through it.

Stage 1, objects and attributes. Five things the system deals with. Each attribute is a fact about one object, such as the pickup time on an order.

Stage 2, relationships. A student places many orders, and each order has one student. Many orders are for one stall. Each order is settled by one payment. One stall has many menu items. The 1 and m say how many, not which ones.

Stage 3, check the abstraction. Nothing here names a screen, a button, a device or a QR code. The same model would still be true if the canteen used a phone app, a web page or a counter kiosk.

Abstract, not physical

The key feature of conceptual design is to "keep things abstract", focusing "on the what rather than the how" (Benyon ch3, Box 3.2, PDF p81). So the model says what the system must know and do. It is not the app. Physical design, from Lesson 14, decides which screens and devices realise it.

Working rule (not stated in the book): if one screen or device could be swapped for another without making the model false, the model is still abstract.

The designer's model and the user's model

Here is how the two pictures connect. The designer has a conception of the system. The book says that conception can only be revealed through the system image: the interface, the behaviour of the system and any documentation (Benyon ch2, PDF p60). The user has to build their own mental model from that system image.

Stage 1, the designer's plan. The conceptual model lives in the designer's hands and the team's diagrams. No user has seen it yet.

Stage 2, the system image. Users never see the plan. They see only the screens, what the system does, and any manual. The designer can steer the user's picture only through this.

Stage 3, the mental model. The user builds their own picture from the system image. It can differ from the plan, because no single designer knows everything the system does (Benyon ch2, PDF p60).

The two pictures are compared in this table.

Conceptual modelMental model
Whose pictureThe designer'sThe user's
How it formsWritten down by the designer, before the system is builtBuilt by the user, by using the system and reading its documentation (Benyon ch2, PDF p60)
How it behavesA stated plan, which the team can discuss and reviseIncomplete, unstable and not always scientific (Norman, in Benyon ch2, PDF p61)

You might reasonably wonder whether the two should match. The book wants the designer's model communicated so clearly that people "will quickly develop a clear mental model" (Benyon ch3, 3.2, PDF p79). That is a goal, not a guarantee. The system image is the only link between the two.

reveal model answer

A conceptual model is the designer's abstract description of the main objects in a system, their attributes and the relationships between them. For the canteen app: the object is Order, the attribute is pickup time, and the relationship is that a Student places many Orders (1 to m). It differs from a mental model in whose picture it is. The conceptual model is the designer's plan, and it names no screen or device. The mental model is the user's belief, built from the system image, and it can be incomplete or unstable.
