Digital signatures

A digital signature lets anyone check who sent a message and that it was not changed. The sender makes it with their private key, and anyone checks it with the sender's public key.

Why this matters: lesson 19 used the public key to hide a message from everyone except one reader. A signature runs the same numbers the other way, so anyone can read the message while the sender is still proved. Focus on: which key signs, which key verifies, and the sign and verify walk. Skip for now: how DSA and ECDSA compute their signatures (deck slides 37–40). How you'll be tested: Lab 2 (page 2) asks you to sign with RSA and verify, so do it by hand, with the Casio for the multiplying. The exam format for signatures is not confirmed.

This is the RSA maths from lesson 19 with the key roles swapped. You already have the pieces: the public pair (e, n) = (7, 33) and the private number d = 3.

Digital signature (new term). (1) What it is: a number the sender computes from the message, using their private key. (2) What value it holds: a whole number smaller than n, for example S = 5 when n = 33. (3) Why it is needed: anyone can check it with the public key, and nobody can make it without the private key.

A signature is judged on three properties. Authenticity proves the origin: the message came from this sender. Integrity proves the message was not changed (both met in lesson 8). Non-repudiation is new: the sender cannot later deny sending it, because only their private key could make the signature.

The rule: sign with the sender's private key (d). Verify with the sender's public key (e). The message travels in plain text, with the signature added beside it.

2. Check: sign a fresh message

Fresh input: sign, then verify

Bob uses the same keys: n = 33, private d = 3, public e = 7. He signs the message M = 2. Find S, then verify it. Try it on paper before you open the reveal.

Reveal, step by step
  1. Sign: S = 23 mod 33 = 8. Eight is already below 33, so no reduction is needed.
  2. Bob sends 2 and 8 together. The message 2 is in plain text.
  3. Verify: 87 mod 33. 82 = 64 → 31. 84 = 31 × 31 = 961 → 4. 86 = 4 × 31 = 124 → 25. 87 = 25 × 8 = 200 → 2.
  4. The result is 2, the same as the message. The signature is valid.

3. Encrypt or sign?

Long messages. Deck slide 44 says RSA is slow on long messages, so the sender first makes a message digest (a short fingerprint of the message) and signs that. The hash function that makes the digest is taught in lesson 21. Until then, treat it as a black box: a short value that changes if the message changes. The walk skips it, so the numbers stay small.

4. Check yourself

Alice wants proof that a message came from Bob. Which key does Bob use to sign it?

Yes. Only Bob holds that key, so only Bob could make the signature. Alice checks it with Bob's public key.
Signing uses the sender's private key. Bob is the sender, so Bob's private key signs.

A friend pastes a scanned picture of a handwritten name under an email. Is this a digital signature?

Right. A scanned name is a picture anyone can copy. A digital signature is a number that only the private-key holder can make.
