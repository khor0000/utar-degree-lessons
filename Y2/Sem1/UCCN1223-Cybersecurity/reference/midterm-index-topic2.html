1. Concepts: what it means and where it is

ConceptOne-line plain meaningSlide no(s)
A. How the OS sits in the machine
Operating system (OS)The layer between users and computer hardware; manages it for programs and people.4
Computer parts the OS managesCPU, RAM, I/O devices, long-term storage.6
KernelThe core of the OS; manages communication between hardware and software (memory, processors, I/O).7
Layer modelHardware at the bottom, users and applications at the top. The OS sits in between.8, 12
Program vs processA program is stored on disk; a process is that program running (loaded into RAM).9
Process ID (PID)Unique non-negative number for each running process; the OS links it to CPU time, memory, user ID, program name.9
APIRules and protocols that let software applications talk to each other and exchange data; lets apps request OS services.10, 12
File systemAn abstraction (a model) of how non-volatile storage is organised into files and folders.11
Root folder and treeFolders nest inside folders; the topmost folder is the root. A drive is a tree of folders.11
File handleAn opaque identifier the OS gives an application when it opens a file.18
File operationsOpen (returns a handle), read/write/execute, close (invalidates the handle). Apps reach files through an API.18
B. File access control (Unix / Linux)
Memory and file system protectionA computer's content is protected by protecting its memory and file system first.14
File permission matrixThe OS checks whether a user or group may read, write or execute a file; each file has owner, group and other permissions.13
ACE and ACLACE = one allow/deny rule for one user or group. ACL = the list of ACEs on one file or folder.18
What Linux controls access toFiles and directories, plus devices (/dev), mounted file systems (/mnt), sockets, pipes, symbolic links.25
Owner and group on every fileStandard for all UNIXes: each file has one owning user and one group.26
ls -lShows permissions as a 10-character string, e.g. -rw-r----- (first character = file type).26
Regular-file permission examplesRead/write/execute for everyone; read-only for everyone; owner-only; owner rw + group r; owner rw + everyone r.27
Directory read, write, executeRead = list names only. Write = create and delete files inside. Execute = enter the folder and see file properties.28
Directory listing lineStarts with d in ls -l output (e.g. drwxr-xr-x).28
Directory permission examplesFull access to all; owner full + group can enter; owner and group full; everyone can list, only owner adds/deletes.29
GUI permission editingIn a file manager (e.g. KDE Konqueror): right-click, Properties, Permissions tab.30
Octal notationEach class (owner, group, others) gets one digit: read = 4, write = 2, execute = 1; add them up.34, 37
Octal values 0 to 70 = no permission, 7 = read + write + execute (full table).34, 35
Octal examples664, 775, 640, 777 (777 = everyone full access, marked dangerous).35
chmod, chown, chgrp exampleschmod changes permissions (also symbolic: g+w, o-rwx, u=rwx,go=). chown changes owner. chgrp changes group. -R applies to contents too.33
Unix permission limitsGroups are restrictive and file creation can be limited, so sometimes more flexibility is needed.36
POSIX ACLs (Linux)Builds on normal Unix permissions and gives finer-grained control for users, groups and other users.36
Root user (superuser)The all-powerful account. Slide 31 is a section heading; the method slide is 32.31, 32
su, su -, sudo, su [-] userWays to become root or another user (see Lists, list 11 for passwords).32
InodeData structure storing a file's metadata (size, owner, permissions, disk location), but not its name or content.20
Hard linkAnother directory entry (name) pointing to the same inode. All hard links share owner, group and permissions. File is deleted only when no hard links remain.19, 20
Symbolic link (symlink)A file that stores the path to a target. Like a Windows shortcut or Mac alias. Removing the target leaves it broken, not deleted.19, 21
Hard vs symbolic link comparedTable on slide 22: differences in new inode, linking directories, crossing file systems, and link count (full detail in the misconceptions table).22
Closed policyDeny everything unless explicitly allowed.23, 24
Open policyAllow everything unless explicitly denied.23, 24
C. Password protection
Dictionary attack (brute force)Hash each candidate word and compare with stored password hashes. About 500,000 words often finds most passwords.15
SaltA random number tied to each user ID and combined with the password before hashing. Makes a dictionary attack more difficult.16
D. Software security
Software securityProtecting software from attacks and vulnerabilities so it works as intended and protects the data it processes.39
Four objectivesPrevent unauthorised access and attacks; protect sensitive data; ensure CIA; maintain reliability.40
CIAConfidentiality (only authorised users access data), Integrity (data stays accurate, not changed without permission), Availability (accessible when needed).40
Recent scenarios2026 Android banking malware (Malaysia); 2025 Malaysia Airports cyberattack; 2025 Jaguar and Land Rover attack.42
Key principlesSecure by design; least privilege; defense in depth; fail securely.43
Common software threatsSQL injection, cross-site scripting (XSS), buffer overflow, broken authentication.44
Security mechanismsAuthentication and authorisation; input validation and sanitisation; encryption and secure key management; secure API usage.45
Security testing typesSAST (source code, before running), DAST (running app), penetration testing (simulated attacker, with permission).46
Why software security mattersSoftware has flaws; threats keep coming; convenience beats security; vulnerabilities grow; everyone's job; same mistakes repeat.41, 47
E. Secure coding
Secure codingTechniques developers use to write code that resists vulnerabilities, attacks and misuse.53
Why secure codingPrevents common attacks; protects sensitive data; reduces downtime and costly breaches; makes apps reliable.53
Eight secure coding practicesInput validation; authentication and authorisation; error handling; session management; secure APIs and libraries; data protection; prevent common vulnerabilities; code review and testing.54, 55
Common vulnerabilities secure coding preventsSQL injection, XSS, buffer overflow, CSRF (cross-site request forgery), broken authentication.56
Insider attackSomeone inside the organisation misuses their access to harm the system or steal data.57
Secure coding vs insidersSecure coding cannot stop all insider attacks, but it reduces the damage (access control, least privilege, input validation, audit logging, secure authentication).57
F. Secure SDLC
SDLCSoftware Development Life Cycle: the stages a software project goes through.49
Secure SDLC (SSDLC)The SDLC with security activities built into every phase, not added at the end.50
Six SSDLC phasesPlanning and security requirements; secure design; secure development; security and testing; secure deployment; maintenance and monitoring.50
Case studiesEquifax (2017, unpatched Apache Struts) and WannaCry (2017, unpatched Windows). Both show how SSDLC would reduce risk.51

2. Pre-empted misconceptions

Looks-like pair, or wrong beliefThe difference / correctionSlide no
Hard link vs symbolic link: "both are just links, they behave the same"Hard link = another name for the same inode, so the data survives if the original name is deleted. Symlink = a small file holding a path, so it breaks if the target is deleted.19, 20, 21
Can a hard link point to a folder, or cross drives?Hard link: no for folders (only root can, the deck says), and no across file systems. Symlink: yes to both.22
"Closed policy" = closed to the public; "open policy" = open to the publicClosed = deny by default, allow only what is explicitly allowed. Open = allow by default, deny only what is explicitly denied.23, 24
Directory "read" means you can open the files insideDirectory read only lists names. You need execute to enter and see file properties. Write lets you add or delete names in the folder.28
Octal 664 on slide 35Slide 35 says 664 is "read-only for everyone else". That is wrong: 664 = owner rw, group rw, others r. Treat the slide label as a deck error.35
su vs sudo: both ask for a password, so they are the samesu and su - ask for the root password. sudo <command> asks for your own password, and only runs one command as root (you must be in the sudoers group).32
Authentication vs authorisationAuthentication = verify who the user is. Authorisation = decide what that verified user may access. The deck lists both under one mechanism.45
Salt stops dictionary attacksSalt makes the attack more difficult. The deck does not say it stops the attack completely.15, 16
SAST vs DAST vs penetration testingSAST reads source code before the app runs. DAST tests the running app from outside. Penetration testing simulates a real attacker (with permission).46
Tree or DAG? (Linux folder structure)Slide 18 says Windows is a tree and Linux is a directed acyclic graph. Slides 11 and 19 call the file system a tree. The deck is inconsistent here; check with the lecturer which one they want.11, 18, 19
